# Epic 1 Retrospective: talenta-core Can Reliably Anchor Any Profile-Section Change

**Format note:** this retrospective uses the BMAD facilitation personas (Amelia — Senior Software
Engineer, Murat — Test Architect, Winston — System Architect) as a narrative voice, not as a
literal multi-person team — the actual work was one AI implementation/review agent across all 6
stories, with the project's human maintainer reviewing at each checkpoint. Every fact below is
drawn from the real story files, code-review findings, `grounding-gaps.md`, and `deferred-work.md`
— nothing here is illustrative or invented. No time/effort estimates appear anywhere in this
document, per this workflow's own standing rule.

## Epic Summary

All 6 stories done: module scaffold + long-lived Fabric connection (1.1), then one route per story
(PERSONAL 1.2, EMPLOYMENT 1.3, EDUCATION 1.4, ADDITIONAL 1.5, PAYROLL 1.6 + the `buildMux`
extraction). All 5 AD-5 routes now share one pipeline (`[auth]→[validate]→[dispatch]→[map-error]→
[respond]`), are provably independent, and are exhaustive (404-by-construction for anything else).

Test suite grew from 17 (end of 1.1) to 88 (final, post-review), 0 failures throughout. Every
patch across all 6 code reviews was applied via a confirmed RED test before the fix and a
confirmed GREEN after — no patch landed without a regression test proving the bug existed.

## What Went Well

**Amelia (Senior Software Engineer):** "The Story 1.2 pipeline abstraction actually held up. Once
`registerProfileSectionRoute` + `routeConfig` existed, Stories 1.3 through 1.5 each needed exactly
one new file plus one line in `main.go` — zero pipeline changes. That's not a claim, it's something
the code reviews independently confirmed each time by finding no pipeline-file diffs to flag."

**Winston (System Architect):** "The dependency-inversion pattern (`newGatewayClientFunc` in Story
1.1, `dispatchFunc` in Story 1.2) meant every stage was unit-testable without a live network. That's
why 88 of the module's tests can run in under a second, and why the two structural gaps we *did*
find (G-35, G-36) are precisely the ones that need a live network or a full stub store — not gaps
in something that could have been tested more carefully with the tools already in hand."

**Murat (Test Architect):** "Every one of the 6 code reviews ran the same three-layer adversarial
process — Blind Hunter, Edge Case Hunter, Acceptance Auditor — and every finding got independently
re-verified against the actual source before being acted on. Two Edge Case Hunter claims across the
epic turned out to be false positives (a nil-bridgectx panic risk that was actually unreachable, an
empty-body nil-pointer risk in `mux_test.go` that `[validate]` already rejects first) and both were
caught by re-reading the code rather than trusted at face value."

## What Could Improve

**Murat (Test Architect):** "One pattern repeated four times and I want to name it plainly: the
`uniqueTestID` helper — built specifically to stop integration tests from colliding against the
live, append-only ledger — was correctly used in the story that introduced the fix (1.3), then
missed in 1.4, missed again in 1.5 *despite 1.4 already having the fix on disk*, and missed a
fourth time in 1.6. The root cause isn't carelessness — it's that all four route stories (1.3-1.6)
were dev-storied back-to-back *before* any of them were code-reviewed, so each one forked from the
same pre-review baseline and never saw the previous story's fix land. The same root cause explains
the pass-through-assertion gap (PERSONAL/EMPLOYMENT had complete `userID`/`newValue` capture;
PAYROLL's initial version had none) and both naming-trap guard tests (1.3's, 1.5's) independently
building a tautological test against their own hardcoded-correct literal instead of the real
`buildMux` wiring."

**Winston (System Architect):** "That last one is worth dwelling on. A test that hardcodes the
literal it's supposed to be checking proves nothing about the shipped code — it would pass even if
`buildMux` were wrong. We caught it in 1.5's review and fixed 1.5's own test, but 1.3's analogous
test still has the same defect (`deferred-work.md`, not reopened since 1.3 was already `done`).
That's a real, still-open item."

**Amelia (Senior Software Engineer):** "Confidentiality leaks happened three separate times —
Story 1.2, 1.5, and 1.6 each had a moment where a new code comment used the real product name,
caught only by the closing `grep -rniE "talenta|mekari"` check. Every single time it was caught
before the story was marked done, so the discipline worked — but three recurrences of the identical
mistake, despite an explicit standing rule, means the risk doesn't go away just because a rule
exists. It needs the grep to actually run, every time, not just be a documented expectation."

**Murat (Test Architect):** "Also worth naming: a stray compiled binary (`go build ./...` silently
writing `integration-bridge/integrationbridge` into the repo root) sat untracked for an unknown
number of story-cycles before Story 1.5's Blind Hunter happened to notice it while grepping broadly.
Nothing in the per-story closing checklist ever ran a `git status` check — only the confidentiality
grep and the test suite. That's a real gap in the routine."

**Winston (System Architect):** "One more: `CLAUDE.md`'s confidentiality register was treated as
covering `integration-bridge/` from the start of this epic, but the document itself wasn't updated
to actually say so until Story 1.3's review caught the drift. A living document that silently falls
behind actual practice is its own kind of technical debt."

## Action Items

**Process:**
1. When authoring multiple structurally-similar sibling stories in one batch (as Stories 1.3-1.6
   were), diff each new story's tests against the most recently *patched* sibling before writing
   them, not just the most recently *dev-storied* one — batching amplified the `uniqueTestID`/
   pass-through/tautology gaps by letting them recur four times before the pattern was named.
2. Add a `git status --porcelain` check alongside the confidentiality grep in the standard
   "before finishing a story" checklist — the stray-binary gap went undetected for a real,
   unknown span of this epic.
3. Update `CLAUDE.md`'s confidentiality register at the moment a new directory starts being
   treated as hard-clean, not retroactively once a review notices the drift.

**Technical debt (tracked, still open):**
4. `grounding-gaps.md` **G-35**: no test proves `buildMux` wires each of the 5 routes to its
   correct, distinct `Hooks` method — AC#3's actual core claim has zero coverage. Closing this
   properly needs a full stub implementation of all 4 `writepaths.Hooks` store interfaces.
5. `grounding-gaps.md` **G-36**: the PAYROLL live-network integration test can't prove byte
   precision survived the real commit, only that a commit succeeded — same pseudonym-opacity
   family as G-34.
6. `deferred-work.md` (Story 1.5 entry): Story 1.3's `TestRegisterProfileSectionRoute_TransferPath_IsNotRegistered`
   still has the tautology defect Story 1.5's own analogous test was fixed for — never reopened
   since 1.3 was already `done`.
7. At least 5 `//go:build integration` tests across this epic have never executed against a live
   network at any point — every "full suite green" claim in this epic's story files has only ever
   meant the non-integration-tagged suite. No CI gate or tracker forces these to eventually run.

## Closing

Epic 1 is complete: all 5 AD-5 routes shipped, sharing one pipeline, provably independent and
exhaustive. The recurring gaps found across Stories 1.3-1.6's reviews are real and instructive but
none were correctness bugs in what shipped — every one was caught and fixed (or honestly deferred
with a tracked reason) before its story was marked `done`. The two genuine structural findings
(G-35, G-36) are honest limits of what this architecture's own confidentiality-by-design choices
allow to be tested, not oversights — and they're now documented for whoever picks up this thread
next, whether that's a future epic or the thesis write-up itself.
