- (decision) Working mode: Coaching path. Deliverables: the spine itself, plus at least one additional human-facing rendering (exact form TBD, to be chosen concretely at Finalize step 5) -- Mr. Chan confirmed he wants both, not spine-only.
- (decision) Paradigm confirmed: backend relay. A small local backend process is the ONLY thing that touches the three real data sources (Caliper CLI stdout via spawn/pipe, local files via fs, Fabric operations /metrics via HTTP poll) -- the browser frontend never touches any of the three directly, always goes through the backend's own relay channel. Rationale: browsers can't read local files/process stdout at all, and Prometheus-style /metrics endpoints typically lack permissive CORS, so direct browser access is infeasible for 2 of 3 sources and fragile for the third.
- (decision) Process shape: two processes, not one. A plain always-running Node backend (Express/Fastify) owns Caliper-process observation, file reads/watches, and operations-endpoint polling with no framework request-lifecycle to fight; a separate Vite+React+shadcn frontend calls it. Chosen over a single Next.js app specifically because the backend must hold long-lived state (spawned/observed process, file watchers, polling loop) across many requests, not re-create it per request -- a plain Node process is architecturally simpler for that than fighting Next's per-request/hot-reload module model. The two-process convenience cost is mitigated with a concurrently-style single start command.
- (decision) Caliper CLI output capture: backend does NOT spawn the Caliper process (UJ-1 requires Mr. Chan to start it himself from the terminal, dashboard never controls process lifecycle). Instead, the terminal invocation redirects stdout to a fixed log file (e.g. 'npx caliper launch manager ... | tee caliper-run.log'), and the backend tails that file. Same file-watching mechanism also covers the raw-latencies JSONL files for Dashboard's live numbers -- one mechanism serves both FR-1/FR-2 and FR-7.
- (decision) Operational decisions confirmed: (1) Backend holds singleton in-memory state (current selected scenario, active file watchers) -- no session/multi-client handling needed, single operator/single browser window per UX spine. (2) Both processes run in production/built mode during the actual defense (dev-mode hot-reload is a live-demo liability); dev mode is fine while building over the next two weeks. (3) New top-level repo directory, e.g. caliper-dashboard/ with backend/ and frontend/ subdirs -- not nested inside qa-tests/performance/, since it's a distinct kind of artifact (live web app) even though it reads that folder's output files. This is a new addition to CLAUDE.md's enumerated top-level-directory list, to be disclosed there at handoff.
- (decision) Relay channel topology: ONE unified SSE stream (/api/stream), not per-concern streams. Every pushed event carries a 'type' field (metric-update, node-status, log-line); frontend dispatches on it. One connection, one reconnect-handling path, chosen for simplicity -- no per-data-type reliability/backpressure need that would justify splitting.
- (decision) Resilience rules confirmed: (1) Failure isolation -- a single data-source failure (operations-endpoint timeout, log file not yet present) must never crash the backend or drop the whole SSE stream; that one data point reports as unavailable (matches UX's '-'/muted-tile treatment) while everything else keeps flowing. (2) Reconnect behavior -- on EventSource auto-reconnect, backend resumes pushing live updates from now, no replay/backfill of missed events.
