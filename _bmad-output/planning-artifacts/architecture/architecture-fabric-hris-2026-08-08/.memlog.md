- (constraint) [ADOPTED, ADR-0022] Host: a new, standalone Go service, sibling to EMS -- embedded in neither talenta-core nor EMS. Not re-decided here.
- (constraint) [ADOPTED, ADR-0022] Calling convention: synchronous HTTP/JSON from talenta-core via a Guzzle client, shared X-Api-Key header, modeled directly on services/ems/BaseEmsService.php's existing production pattern. The service must accept that exact shape of inbound call.
- (constraint) [ADOPTED, ADR-0022] Call sites: 4 real PHP commit points cover 5 profile sections -- PERSONAL and PAYROLL share one call (InboxController::updateChangeData()). The bridge's route/operation shape must accommodate this many-to-fewer mapping, not assume 1:1.
- (constraint) [ADOPTED, ADR-0014] In-band constraint: no queue, no async relay -- the bridge call blocks the same talenta-core request. This bounds the bridge's own request/error-handling paradigm (a slow or hung bridge call IS a talenta-core write-path outage).
- (constraint) [existing code, brownfield] The bridge wraps write-path-integration/writepaths.Hooks (Go, already built and tested) -- a struct with 5 exported methods (UpdatePersonalData, ApproveEmploymentTransfer, RecordEducationHistory, ApproveFamilyDataChange, UpdatePayrollBankAccount), each signature (ctx, employeeInternalID, userID string, newValue, document []byte) ([]byte, error), plus an OnPartialFailure callback hook. The bridge does not re-implement domain logic; it is a transport adapter in front of an already-encapsulated package.
- (constraint) [ADR-0022 Follow-up, deliberately NOT decided by ADR-0022] Open, still unresolved: bridge module/deployment layout; transport security (mTLS vs BaseEmsService's TLS+API-key precedent, needs security-architect confirmation); circuit-breaker/fallback behavior if the bridge or Fabric is unavailable. These are candidates for THIS spine to close, since they are exactly the invariants independent builders of this one service could diverge on.
- (direction) Working mode: Coaching (user choice). Deliverable: spine only, no rendered doc. Scope: the integration-bridge service's own internal architecture, not the platform-wide Fabric design (which lives in agent-suite/05-adr/).
- (decision) AD-1: Design paradigm = middleware pipeline (fixed chain: auth -> request validation -> dispatch to the matching writepaths.Hooks method -> error mapping -> response), applied uniformly to every route. Binds: all bridge routes. Prevents: each handler independently re-deriving auth/validation/error-mapping logic and silently diverging on it. Rule: no route may call a Hooks method directly from its own handler body outside the shared pipeline. User-confirmed over (1) thin per-handler adapter and (3) command-per-operation.
- (decision) AD-2: Module/deployment layout = new top-level directory 'integration-bridge/' (proposed name, user confirmed same-repo placement), own go.mod, go.mod replace-directive pointing at ../write-path-integration/writepaths -- matching the fabric-network/tools/* precedent (standalone module depending on, not sharing a workspace with, what it needs). Binds: this service's build/dependency setup. Prevents: splitting into a separate repo prematurely, and blending an HTTP-facing service into the write-path-integration/go.work workspace's 4 pure-library modules. Rule: integration-bridge/ has its own go.mod; it is NOT added to write-path-integration/go.work. User-confirmed over (1) 5th go.work member and (2) separate repo.
- (decision) AD-3: Error-mapping convention = HTTP status is pure transport (2xx=bridge processed the request, 4xx=bad input from talenta-core, 5xx=bridge itself is broken). ALL business outcome lives in a body field 'status': committed | partial_failure | rejected | error. talenta-core's retry/idempotency logic reads status, never the HTTP code. Binds: every route's response shape. Prevents: a future handler treating any 5xx as safely-retryable, which is false for the one typed error (*writepaths.PartialFailureError) that means the operational-DB write already landed. Rule: the error-mapping stage of the AD-1 pipeline is the ONLY place that sets 'status'; no handler sets it directly. User-confirmed over (1) status-code-carries-meaning.
- (decision) AD-4: Timeout/circuit-breaker = one shared, centrally-configured timeout budget (context.WithTimeout), enforced once in the AD-1 pipeline's dispatch stage, applied identically to every route. On timeout, status = 'partial_failure' (same as a real *writepaths.PartialFailureError), NOT a separate 'timeout' category -- grounded in the verified fact that every one of the 5 Hooks methods calls Store.SaveSection (operational-DB write) and returns before anchor() runs, so a timeout mid-anchor has the identical consequence: DB write already landed, ledger state uncertain. Binds: every route's timeout handling. Prevents: per-route timeout policy drift, and a spurious 'timeout' status category that would need its own (redundant) not-safe-to-retry handling in talenta-core. User-confirmed.
- (question) OPEN, unresolved by this spine, verify before build: when the bridge cancels its context on timeout, does that actually abort the in-flight Fabric submission inside gatewayclient/GatewayClient.SubmitRecordProfileSection, or does it only abandon the bridge's local wait while Fabric keeps processing an already-sent transaction? If the latter, a timeout-triggered partial_failure could still race a transaction that commits moments later, which would need reconciling (e.g. via GetProfileHistory), not just reporting. Owner: backend-engineer, verify against gatewayclient's real submit implementation before relying on AD-4's timeout=partial_failure equivalence in production. User-confirmed deferring rather than asserting an answer.
- (decision) AD-5: Route/operation shape = 5 distinct operations, one per profile section (PERSONAL, EMPLOYMENT, EDUCATION, ADDITIONAL, PAYROLL), each mapping 1:1 to the matching writepaths.Hooks method. The bridge does NOT collapse PERSONAL+PAYROLL into one operation, even though both share one real PHP call site (InboxController::updateChangeData()) -- that is an accidental fact about one caller's own internals, not a property of the bridge's own API shape. Binds: the bridge's API contract. Prevents: leaking a caller-specific implementation coincidence into a contract a future second caller might not share. Rule: exactly 5 operations, named after the 5 ProfileSection enum values already ratified on-chain (chaincode/asset.go), never fewer. User-confirmed; corrects an earlier constraint-log over-inference (entry citing a 'many-to-fewer mapping' requirement -- that requirement does not actually exist, per this decision).
- (decision) AD-6: Stack = net/http stdlib only, no router/middleware framework -- Go 1.22+ enhanced ServeMux (method+path patterns) covers all 5 routes. AD-1's pipeline implemented as plain http.Handler-wrapping functions. Binds: HTTP layer dependencies. Prevents: an unnecessary third-party router/framework dependency for 5 simple POST routes. Rule: no HTTP router/framework import beyond net/http. User-confirmed.
- (convention) Request envelope (JSON body): employeeInternalID, userID (actor -- read directly by talenta-core at the call site per REAL-INTEGRATION-TRIGGER-FLOW.md's actor-identity gap, never resolved by the bridge), newValue, document (optional, base64) -- mirrors the matching Hooks method's own signature exactly, no bridge-invented fields.
- (convention) Response envelope (JSON body): {status: committed|partial_failure|rejected|error, recordID?: string, detail?: string} per AD-3.
- (convention) Auth: X-Api-Key header, matching services/ems/BaseEmsService.php's existing production precedent (AD-2).
- (convention) Error classification: errors.As for *writepaths.PartialFailureError only; every other error is opaque -- the bridge never re-implements gateway-client's own private string-matched sentinel classification (isExpectedRetryableRejection/isNotFoundRejection stay internal to gateway-client).
- (constraint) Source tree (seed): integration-bridge/{go.mod, main.go, handlers.go (5 thin handlers), pipeline.go (AD-1 chain), pipeline_test.go}. Exactly 5 handlers per AD-5, each named after its ProfileSection enum value.
- (question) OPEN, Deferred: exact timeout duration for AD-4's shared budget -- needs tuning against QA-4's real measured Fabric latencies (qa-tests/performance/RESULTS.md), not picked arbitrarily here.
- (question) OPEN, Deferred, owner security-architect: transport security beyond X-Api-Key (mTLS vs the BaseEmsService TLS+API-key-only precedent) -- ADR-0022 already flagged this needs explicit confirmation, not silent inheritance of the precedent.
- (question) OPEN, Deferred: the 3 PAYROLL write surfaces this bridge does not cover as scoped (MyInfoController::actionEditPayrollInfo, bulk import, cron, third-party importer) -- separate hook-and-bridge-call decision, per ADR-0022's own disclosed gap.
