# GO-TESTING — EMS test conventions (unit, mocks, integration, specs, CI)

> **Scope.** How tests are written, mocked, and run in the real `employee-management-service` (EMS)
> repo, plus the spec-kit (`specs/`) and QA (`qa-tests/`) conventions that bracket them. Grounded in
> `/Users/chan/www/employee-management-service`. For the layering under test read
> `GO-ARCHITECTURE.md`; for the language-agnostic testing rubric,
> `> See coding-standards-backend/references/principles.md`.

## 1. How tests run

- **Framework:** stdlib `testing` + **`github.com/stretchr/testify`** (`assert`, `require`, `mock`)
  `[code: ems/go.mod]`, `[code: ems/internal/user/handler/handler_test.go]`.
- **Make target:** `make test` runs `go fmt ./...`, `go vet ./...`, then `go test -v -coverprofile=coverage.out`
  over **all packages except the generated datasource layer** (`go list ./... | grep -v ./internal/datasource`)
  `[code: ems/Makefile]`. On macOS it adds `-ldflags=-linkmode=external` `[code: ems/Makefile]`.
- **Per-module target** exists too, e.g. `make test-company` scopes to `./internal/company/...` and
  prints module coverage `[code: ems/Makefile]`.
- **Coverage:** `make coverage` opens the HTML report from `coverage.out`
  `[code: ems/Makefile]`.
- Tests are **co-located** as `*_test.go` next to the code they cover (e.g.
  `pkg/pii/mask_test.go`, `internal/base/authz/guard_test.go`, `internal/user/handler/handler_test.go`).

## 2. Table-driven unit tests

The house style for pure functions is a map or slice of cases. `pkg/pii/mask_test.go` iterates a
`map[input]want` and asserts byte-for-byte equality, with the comment noting the vectors mirror
talenta-core's `MaskHelperTest.php` so both services mask identically
`[code: ems/pkg/pii/mask_test.go]`:

```go
cases := map[string]string{
    "+628123456890": "+62812****890",
    "12345678":      "12345678", // ≤8 chars → passthrough
}
for in, want := range cases {
    if got := MaskPhone(in); got != want { t.Errorf(...) }
}
```

Behavioural units use **`t.Run` subtests** with descriptive names, as in the Guard tests
("allows resource owned by the authenticated company", "masks cross-tenant resource as 404")
`[code: ems/internal/base/authz/guard_test.go]`.

## 3. Mocks — mockery

- Mocks are **generated by mockery** (`v2.53.5`) and committed under a `mocks/` sub-package next to
  each interface: `internal/education/repository/mocks/Repository.go`,
  `internal/user/service/mocks/Service.go`, `internal/base/service/ulms/mocks/ULMSService.go`
  `[code: ems/internal/education/repository/mocks/Repository.go]`. They carry
  `// Code generated by mockery v2.53.5. DO NOT EDIT.`
- Because every layer depends on an **interface** (`Repository`, `Service`, `ULMSService`,
  `AuthorizationGuard`), a unit test injects the generated mock and drives it with
  `testify/mock` (`.On(...).Return(...)`) `[code: ems/internal/user/handler/handler_test.go]`.
- **Recommendation:** regenerate, don't hand-edit, mocks; a new anchor-service interface should get
  a `mocks/` peer the same way so its consumers stay unit-testable.

## 4. HTTP handler tests

Handler tests build a real-ish `*app.Context` without a live server, using `httptest` +
`gin.CreateTestContext` + `app.NewContext`, then assert on the returned `*server.Response`
`[code: ems/internal/user/handler/handler_test.go]`:

```go
ginCtx, _ := gin.CreateTestContext(httptest.NewRecorder())
ginCtx.Request = req
ctx := app.NewContext(ginCtx, &appconf.Config{}, constant.AUTH_SCOPE_COMPANY, false, identity, company)
```

Test fixtures build identities directly (`createAdminUser`, `createNonAdminUser`) so RBAC branches
(`RoleAdmin` vs others) can be exercised deterministically
`[code: ems/internal/user/handler/handler_test.go]`. The Guard's registry is constructed in-test with
a stub `ResolverFunc`, so ownership-masking logic is verified without a DB
`[code: ems/internal/base/authz/guard_test.go]`.

## 5. Integration tests — `pkg/testutil`

For repository/DB-touching tests there is a real-dependency harness, `testutil.TestSuite`
`[code: ems/pkg/testutil/suite.go]`:

- Loads `.env.test` (walks up to the repo root via `runtime.Caller`), then
  `appconf.InitAppConfigForTest()` `[code: ems/pkg/testutil/suite.go]`.
- Opens a **real MySQL** connection (GORM, silent logger) and a **real Redis** client, pinging both
  in `Setup()` `[code: ems/pkg/testutil/suite.go]`.
- `AutoMigrate`s a small set of tables (`TblCompany`, `TblCompanySetting`, …) for the suite
  `[code: ems/pkg/testutil/suite.go]`.
- **Isolation is transaction-per-test:** `BeforeTest()` opens a transaction and flushes Redis;
  `AfterTest()` rolls it back; `GetDB()` returns the in-flight transaction so nothing persists
  `[code: ems/pkg/testutil/suite.go]`. `Run(name, subtest)` wraps a subtest in that begin/rollback.
- `Assert()` returns a `testify/assert.Assertions` bound to the suite's `*testing.T`
  `[code: ems/pkg/testutil/suite.go]`.

This mirrors why the CI `test` step needs services and why `APP_ENV=test` selects the test config
path (`InitAppConfigForTest`) `[code: ems/app/appconf/config.go]`.

## 6. Linting & formatting gates

`.golangci.yml` pins Go 1.21 and enables **govet, staticcheck, ineffassign, misspell, gocritic**;
`tests: false` (linters skip `_test.go`); goimports `local-prefixes` is the module path; gocritic
adds `hugeParam`, `rangeValCopy`, `unnecessaryBlock` `[code: ems/.golangci.yml]`. `make test` also
runs `go fmt` + `go vet` before the tests `[code: ems/Makefile]`. Husky pre-commit hooks exist under
`.husky/` `[code: ems/package.json]`.

## 7. CI pipeline (Bitbucket)

`bitbucket-pipelines.yml` defines a **Unit test** step on a `golang:1.21` self-hosted alicloud
runner: it vendors deps and runs
`APP_ENV=test go test -v -mod=vendor -coverprofile=coverage.out \`go list ./... | grep -v ./internal/datasource\``
then `go tool cover -func=coverage.out` `[code: ems/bitbucket-pipelines.yml]`. Build/deploy steps
(`buildImageStaging`, `deployStaging`) run only on `master`/`deployment-manifest` via `mkrctl`
`[code: ems/bitbucket-pipelines.yml]`. See `GO-DEPLOYMENT.md`.

## 8. Feature specs — spec-kit (`specs/`)

New features are specified with GitHub **spec-kit** under `specs/NNN-<slug>/`, each folder holding
`spec.md`, `plan.md`, `tasks.md`, `data-model.md`, `research.md`, plus `contracts/` and `checklists/`
`[code: ems/specs/002-bulk-import-employee-go/]`. `plan.md` carries a **Technical Context** block that
names Language/Version, Primary Dependencies, Storage, **Testing** ("`go test ./...` — unit tests
co-located in `_test.go`; mocks via `mockery`"), and explicit Performance Goals
`[code: ems/specs/002-bulk-import-employee-go/plan.md]`. Config for spec-kit lives in `.specify/`
`[code: ems/.specify/]`.

**Recommendation:** author the Fabric anchor-service under the same `specs/` convention so its test
strategy and acceptance criteria are captured before code — this is also where gap **G-14**
(concrete gate acceptance criteria) would be pinned down.

## 9. QA security matrices — `qa-tests/`

Manual/exploratory security verification lives as `.http` files (VS Code REST Client / JetBrains
HTTP client). `qa-tests/security/launchpad-idor.http` is an IDOR / tenant-escape matrix run against a
deployment with `AUTH_HARDENING_ENFORCE=true`: it enumerates tenant-escape via `X-Scope`/`X-Company-ID`
(expect 401), IDOR via path `:id` (expect **404 masked**), privilege-escalation via the ignore-role
header (expect denied), and legitimate own-company + consultant controls (expect 200)
`[code: ems/qa-tests/security/launchpad-idor.http]`. These cases are the executable expression of the
Guard + auth-hardening behaviour described in `GO-SECURITY.md` and map to the OWASP-API frame (E5).

## 10. Coverage expectations & gaps

- The generated `internal/datasource` layer is deliberately **out of coverage scope**
  `[code: ems/Makefile]`, `[code: ems/bitbucket-pipelines.yml]`.
- There is **no `migrations/` in EMS** — DDL on the shared MySQL is owned by talenta-core (gap
  **G-16**), so integration tests `AutoMigrate` only the tables they need rather than owning the
  schema `[code: ems/pkg/testutil/suite.go]`.
- Per-tenant PII-encryption rollout is phased (gap **G-21**): tests must not assume encrypted columns
  are populated or plain columns are empty; drive reads/writes through the app layer, not raw columns
  (matches the plugin's company-gated behaviour) `[code: ems/pkg/db/encryption_plugins.go]`.
